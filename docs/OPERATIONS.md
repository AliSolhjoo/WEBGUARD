# Local operations and deployment notes

## Local process model

The local setup runs three independent processes: Django API, scan worker, and Vite development server. Start/stop each from its PowerShell window. Closing the worker pauses queued scans; it does not delete them.

## Database lifecycle

- SQLite is used by default and is suitable for local single-user or low-concurrency development.
- Back up `backend/db.sqlite3` before upgrades or destructive operations.
- Do not place SQLite on a network share.
- Move to PostgreSQL before multiple workers or production traffic.
- Migration files are generated by the setup script for the initial local install. Commit generated migration files when using the repository as a shared team project.

## Worker operation

`python manage.py run_scan_worker` polls for pending scans and processes one job at a time. It checks for stale `running` rows each minute and marks jobs older than five minutes as `failed`; it does not automatically retry interrupted jobs. Use `--once` to process at most one pending scan, useful for tests or controlled maintenance. Keep exactly one local worker process with SQLite.

## Environment

`.env.example` contains safe local defaults. Never commit `.env`. Production must have `DEBUG=false`, a strong secret key, explicit allowed hosts and CORS origins, HTTPS, and a persistent PostgreSQL database. Secure deployment needs a separate isolated scanner environment and egress firewall controls as described in `SECURITY.md`.

## Backups and data retention

The database stores organizations, asset verification tokens, scan results, findings, reports metadata and audit events. Protect database backups as sensitive security data. Define a retention policy before onboarding customers; do not retain verification challenges or scan evidence indefinitely without a business/legal reason.


## Domain ownership verification troubleshooting

Adding an asset only creates a DNS TXT challenge; it does not publish that record automatically. In the authoritative DNS control panel for the domain, create a TXT record using the exact value displayed by the WEBGUARD modal. The full record name is `_webguard-verify.<your-domain>`. Some DNS providers automatically append the zone name; with those providers, enter only `_webguard-verify` in the Host/Name field to avoid duplicating the domain suffix.

After saving the record, allow DNS publication according to the provider's TTL, then return to WEBGUARD and click **Verify DNS record**. A failed check leaves the modal open and displays the API's error inline. A missing record is a client-correctable HTTP 400 response; an unavailable or timing-out DNS resolver is reported as HTTP 503 and can be retried later. Verification is not automatic or continuously polled.

The Vite duplicate-object-key warnings in older V2 builds came from repeated Persian translation keys. The current source keeps one translation per key.
